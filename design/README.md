# 筑衡产品流程与界面设计交付

这份目录供工业设计与前端共同讨论。当前是第一阶段的流程和信息层级稿，不是已经上线的产品页面，也不是专业结论。

## 一句话说明任务

让首次接触项目的人在一次演示中看懂：**哪些方案不能选、剩余方案各有什么取舍、为什么当前视角下推荐某个方案**。

## 第一阶段：流程与线框（优先完成）

交付物是可点击的 [低保真流程原型](prototype/index.html)、[二维方案对比视觉稿](prototype/comparison.html) 和以下页面决策。浏览器直接打开 HTML 文件即可查看；不需要 Figma 账号。对比视觉稿使用仓库现有的虚构评分与四个角色权重，演示图表、排名与合规提醒的布局。下载时保留同目录下的 CSS、JS 与数据文件。

### 二维方案对比稿 V2

- **维度矩阵**：每列一个方案，每行一个评价维度，共 20 个评分格。全表共用 0–100 的颜色刻度，颜色越深分数越高；合规方案中的维度最高值加菱形标记。权重显示在行标题，排名和贴近度显示在底行。
- **比较基准**：在任一合规方案列设为基准后，其他格子显示相对分差。数字来自原始快照，最后才舍入；不是用显示值相减。
- **分数追溯**：点击格子，下方显示该维度的指标、原始值、评分公式、维度内权重与指标分数。当前专业来源待确认的状态明确保留。
- **二维取舍图**：自由选择横纵轴，所有坐标使用 0–100 分；选择重复维度时自动交换两轴。每个点代表一套方案，点的位置只反映选定的两个维度，不能代替四维加权排名。
- **违规方案**：矩阵中 B 列用斜纹与文字区分，不参与默认排名；坐标图默认不显示 B，可以单独勾选显示。它的分数来自评估快照，未用零分代替违规状态。
- **角色切换与导出**：切换角色同步更新权重和贴近度，维度分数与坐标保持不变。当前视图可导出独立 SVG，适合放进设计评审材料。

页面不依赖远程字体、第三方 CDN 或后端服务。运行 `node design/sync-comparison-data.cjs` 可从仓库快照更新原型数据，不需复制或手填专业数值。

浏览器验收覆盖基准差值、角色权重、分数详情、坐标轴交换、B 的显示开关、SVG 导出与 390px 窄屏布局，无页面运行时错误。已检查实际页面截图：[矩阵截图](evidence/comparison-matrix.png)、[取舍图截图](evidence/comparison-map.png)。[矩阵 SVG 示例](evidence/comparison-matrix.svg)展示施工总包视角与 D 基准；[取舍图 SVG 示例](evidence/comparison-map.svg)展示交换轴后包含 B 的坐标图。

| 步骤 | 用户要解决的问题 | 页面必须说清楚的内容 | 建议组件 |
| --- | --- | --- | --- |
| 1. 方案录入 | 比较哪些方案？ | 项目条件与方案条件分开；字段单位、必填项、缺项提示；手动录入和 Excel 导入入口 | Form、Steps、Alert、Upload |
| 2. 合规检查 | 哪些方案存在硬约束问题？ | 通过/警告/不通过三种状态；规则 ID、实际值、阈值、出处；错误级不通过方案默认不参与排名 | Alert、Tag、Table、Drawer |
| 3. 多方案比选 | 谁领先，取舍在哪里？ | 当前角色、第一名、参与排名的方案、四维差异、分数溯源入口 | Card、Table、Progress、ECharts |
| 4. 角色与权重 | 换个视角会怎样？ | 四类角色、四维权重、排名及贴近度变化；自定义权重与预设角色明确区分 | Segmented、Slider、ECharts |
| 5. What-if | 改一个参数会怎样？ | 修改前值、新值、原方案与副本、重新计算后的指标和名次变化 | Form、Descriptions、Table |
| 6. 最终报告 | 如何向他人说明决定？ | 结论、合规问题、四维取舍、稳健性、修改建议、可追溯入口和导出 | Typography、Anchor、Drawer |

信息顺序建议：**结论 → 关键原因 → 详细证据 → 下一步操作**。首次进入比选看板时，先显示推荐方案、违规方案和主要差异。二维矩阵负责完整比较，取舍坐标图用于探索两维差异；雷达图可作为后续辅助视图。

### 第一阶段完成标准

1. 不读项目文档的人能独立走完六步，并说出“B 为什么不参与排名”。
2. 每一屏有明确的主操作；错误、警告和普通信息不会混淆。
3. 任何排名都能看到当前角色或权重；任何分数都能找到原始值和依据。
4. 开发同学能把每个设计块对应到现有 Ant Design/ECharts 组件和后端数据。

## 第二阶段：界面视觉与开发交接

在第一阶段通过团队讨论后，定一套可复用的视觉规范：颜色与状态色、字体层级、间距、按钮、卡片、表格、图表线色和图例、空状态、加载与错误状态。交付桌面端关键页面和窄屏布局，并为违规提示、分数溯源、报告数字异常等重要状态单独出图。高保真稿先与前端同学确认可用组件，再落实到现有页面。

交接时给出每个页面的操作说明、文案、数据字段、状态图和需要开发修改的优先级。工业设计负责用户理解与视觉表达；建筑和土木专业组负责规则阈值、权重、条文出处，前端负责接入真实计算与交互。

## 第三阶段：演示与答辩材料

按不超过五分钟的故事线准备视频脚本、录屏、字幕与剪辑：场景和问题 → 录入及合规 → 方案比较 → 权重变化 → What-if → 报告与价值。同步统一答辩 PPT、技术架构图与界面的色彩和术语。脚本中的每个镜头必须能由当前可运行产品或明确标注的示例素材支撑。

## 当前原型与正式系统的边界

- 原型是静态演示页面；输入框和按钮用于讨论操作方式，**不会调用后端计算**。其中示例值不作工程依据。
- 当前仓库的四个预设角色在原始样例上的名次相同。若视频需要演示名次变化，可使用已有的自定义权重演示；若要展示角色切换即换位，需要专业组确认可用的新样例数据。
- 当前真实模式的 What-if 入口支持修改标准层重复率并创建副本；策划书里的“改用 MiC”需要另行确认数据和交互实现。
- T10 规范条文检索尚未完成；条文原文区域只能作为预留设计。现有规则、权重与方案有示例内容，专业组确认前不得将其作为真实工程验证或比赛结论。

## 建议的下一轮评审

请团队用原型走一遍六步，并分别记录：哪里看不懂、哪项信息应该先看到、哪一步缺少操作入口。前端同学核对组件与数据可实现性；专业组核对术语、违规说明和正式依据。根据反馈改线框，再进入高保真和视频脚本。
