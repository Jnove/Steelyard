## 一、留给专业组（土木 / 建筑）

### 1.1 先看清楚现在 `rules/` 里是什么

T3 把规则引擎搭好了：`rules/*.yaml` 能被加载、校验、跑出分数，报告里的数字都是**真算出来的**。

但**规则内容尚未经过专业核定**。截至 2026-10-12，`rules/` 下 12 条规则全部是**格式示例**：

- 阈值和分段点都是随手取的，只为演示"YAML 怎么写、引擎怎么跑"；
- 每条的 `name` 都带「【示例】」前缀；
- 每条的 `source` 都是 `TODO(专业组)：示例数值，正式条文号待补`；
- **没有编造任何规范条文号**。

> 未核定规则与虚构方案可在明确标注后展示工作流和计算过程，但不能充当工程验证、规范合规或结构安全结论，也不能作为实际成效证据。主案例中的专业判断须按其真实来源和适用范围解释。

### 1.2 怎么改一条规则

完整教程在 [rules-guide.md](rules-guide.md)（给没写过代码的同学写的，不用装 Python，
浏览器里就能改）。要用到的两张表：

- 字段名、单位、派生量：[fields.generated.md](fields.generated.md)
- 空白模板与字段说明：[`rules/_template.yaml`](../rules/_template.yaml)

改完**一定要跑一遍校验**，它会用中文告诉你哪一行错了、怎么改：

```bash
uv run --project backend python scripts/check_rules.py
```

### 1.7 待定：窗墙比要不要按朝向分别定规则

初筛后 P1；如主案例必须使用该指标，只先核定其实际涉及的朝向和依据，不扩展评价范围。

`window_wall_ratio` 这个字段存的是**各朝向各一个值**（南 / 北 / 东 / 西）。
现在**一条规则都没用到它**，因为要先知道你们想怎么判：

- **方案 A**：按朝向分别定，比如"南向窗墙比 ≤ 0.40，北向 ≤ 0.30"；
- **方案 B**：只看一个汇总值，比如所有朝向的最大值或面积加权平均。

引擎已支持 `window_wall_ratio['南']` 这种固定字符串键取值，技术限制已解除。
按朝向还是汇总评价、阈值与依据仍由专业组确定；汇总评价如需面积权重，还需明确输入字段。
`unit_mix` 也支持固定字符串键，但户型分类与评价方法尚未核定。

- [ ] 定方案 A 还是 B（A 的话请给出要管哪几个朝向）

### 1.9 确认完之后怎么收尾

每条规则定稿时做四件事：

1. 去掉 `name` 里的「**【示例】**」前缀；
2. 把 `source` 从 `TODO(专业组)：...` 换成真实出处——
   规范原文写「规范编号 空格 第 X 条」，组内经验判断写「经验规则（XX组）：一句话理由」
   （格式见 [rules-guide.md §5](rules-guide.md#5-source-字段怎么填)）；
3. 跑 `scripts/check_rules.py`，**所有「错误」都要清零**（「警告」里的 TODO 提醒会自动消失）；
4. 提 PR，描述里写清楚改了哪些数值、参考了哪条规范、为什么这么改。

全部专业内容定稿后的目标是 `check_rules` **0 个错误、0 个警告**，不是本轮初筛必须清空所有占位的数量要求。
当前仍有规则与角色模板的 TODO，计数以本次运行输出为准；未核定条目继续保留标记，不得计入已验收的专业依据。
