# 筑衡界面改造简案

日期：2026-10-12。状态：待实施，供设计与开发对齐。

本轮硬截止为 2026-10-15 24:00（UTC+8）；内部计划在 2026-10-14 12:00 冻结版本。日程与分工统一见 [线上初筛交付计划](submission-plan.md)。

## 目标

让评委和首次访问的用户，无需先理解建筑指标与决策算法，就能看懂筑衡帮助谁解决什么问题、推荐为什么成立，以及怎样验证和调整结论。

操作路径围绕 **问题 → 取舍 → 依据 → 调整后的变化** 展开。现有排名、偏好调整、计算追溯、对话和报告继续使用，重点调整入口与信息层级。

## 页面调整与优先级

| 页面 | 调整方向 | 优先级 |
| --- | --- | --- |
| 首页 | 用一个具体的建筑方案取舍场景说明价值；突出“体验示例比选”，注明虚构示例，同时保留“创建项目”。示例体验应与用户项目隔离，避免访问者先填写大量参数。 | P0 |
| 对比看板 | 第一屏展示当前偏好、可参与比较的方案、建议优先讨论的方案、主要优势、需要接受的取舍和待确认事项。雷达图、算法指标与敏感性分析放入详细比较区域。 | P0 |
| 对话与报告 | 在结论旁提供“为什么推荐”“换一种关注重点”“修改一个参数”，衔接现有追问与 What-if；展示调整前后的实际变化和报告入口。 | P0 |
| 方案录入 | 按用途组织参数，说明它影响哪类判断，保留字段单位、校验和 Excel 导入；示例体验直接带入已有数据。 | P1 |

三个 P0 目标在 2026-10-13 完成首轮联调，冻结前完成体验走查；参数录入分组与更多交互细节在通过初筛后继续打磨。

## 展示与实现原则

- **结论带条件。** 使用“当前偏好与已录入规则下，建议优先讨论……”；优势与取舍必须来自实际比较结果，不强行凑满固定条数。偏好改变后名次未变，也如实解释。
- **专业术语可展开。** 主界面用容易理解的说明，计算方法保留 AHP、TOPSIS、CR 等术语。比较指数不等于合格率，CR 不等于工程结论可信度。
- **判断范围明确。** “合规检查通过”改为“已录入规则检查通过”；结构维度说明为当前规则下的结构相关指标评分。显示真实来源和待核定状态，保留 `TODO(专业组)`；“覆盖率”明确为评分数据覆盖率。未实现或未核定的造价、碳排与条文检索能力不作为现有成果宣传。
- **AI 的作用可见。** 呈现请求理解、实际工具调用与结果解释，数值继续由确定性引擎计算。明确演示或模型状态，不用预制过程冒充真实执行。
- **上下文连续。** 从看板进入追问或报告时保留项目、方案和角色口径；自定义权重无法沿用时明确提示。What-if 创建副本，展示修改项与前后对比，原方案保持不变。
- **沿用现有基础。** 保留品牌、路由、技术栈和字段元数据生成方式，复用现有 REST / SSE、追溯抽屉与报告能力。具体字段和事件以现有接口为准，不另写一套评分或参数定义。

## 验收方式

1. 请一位不了解建筑的同学独立体验，能说清目标用户、核心取舍、推荐依据及 AI 的作用。
2. 能从示例入口走通“看结论 → 查依据 → 换偏好或改参数 → 比较变化 → 查看报告”，关键操作不依赖口头提示。
3. 示例与真实数据边界清楚，待核定依据可见；页面结论、计算追溯和最终报告口径一致，错误与加载状态可理解。

建议工业设计同学负责信息层级、页面布局与体验走查，技术组负责交互衔接，专业组核对术语和结论边界。2026-10-14 冻结后只处理阻断体验或影响事实准确性的修复；修改后同步核对视频、报告与说明文档。
