# 演示案例：杭州钱塘 · 保障性租赁住房 · 装配式决策（虚构）

> 本目录所有 JSON 都是**虚构数据**，用于工作流演示与视频录制，
> **不得**作为工程验证、专业结论或答辩证据。每个文件顶层都带 `_note` 声明。

> **需要真实地块时，本目录不是唯一选择**，仓库里现在有三条数据线：
>
> | 目录 | 地块 | 方案 | 适用场合 |
> | --- | --- | --- | --- |
> | `data/schemes/mock/` | 虚构 | 虚构 | T6 回归测试与前端离线快照，**不要动** |
> | `data/schemes/demo-qiantang-fictional/`（本目录） | 虚构 | 虚构 | 需要 6 套方案、支配关系与配对演示时最好用 |
> | `data/schemes/qiantang-real/` | **真实（钱塘前进公租房一期）** | 演示自拟 | 需要「真实项目」时用它 |
>
> 真实地块候选与出处汇总见 [演示案例候选清单](../../docs/demo-candidates.md)。

这套案例是为「线上初筛四项材料」准备的**主案例候选**：一个地块、五套合规方案 +
一个 What-if 副本，数字与结论都由当前的规则引擎实算得出（证据见 `_check.txt` /
`_check-gb.txt` / `_check.json`，由本目录 README 末尾的命令生成）。

## 一、这个案例想讲什么

一句话：**同一个地块上，「住得舒服」「造得省事」和「政策上划算」是三件事，
系统不替你选，但会把每条路线的代价算清楚。**

三条故事线（都已用当前规则集验证过）：

1. **角色不同，赢家真的会变。** A 是唯一在「住户」视角下排第一的方案（0.785），
   在政府 / 开发企业 / 施工单位 / 设计单位视角下都掉到第 4（0.26–0.49）；
   B 则相反，四个非住户角色全部排第一（0.70–0.88）。这不是预设的剧情，是
   `rules/weights.yaml` 里五套初始权重的直接结果。
2. **合规只是入场券。** E 没有任何硬约束问题，但被 A、B′、D 同时支配，
   五个视角下都垫底（贴近度 0.012–0.038）。系统能指出「这个方案在任何一套
   权重下都不值得再讨论」，这比只说「谁对谁错」更有说服力。
3. **改一个选项，整条路线就变了。** B 是 MiC 模块化，B′ 是把它改成现浇后的
   What-if 副本：硬约束依然全过，但绿色维度从 100.00 掉到 68.00、施工友好从
   100.00 掉到 61.11，结果**连 D（10 层的常规做法）都不如**。这正是「What-if
   创建副本、原方案保持不变」要演示的东西。

## 二、地块条件（项目层）

| 字段 | 取值 | 说明 |
| --- | --- | --- |
| 用地面积 | 18,000 m² | 虚构，约 1.8 ha |
| 容积率上限 | 2.5 | 五套方案实际 2.13–2.44 |
| 建筑密度上限 | 0.22 | 按 GB 50180—2018 表4.0.2 Ⅲ 气候区高层住宅 |
| 限高上限 | **51 m** | 刻意压到刚好等于「17 层 × 3.0 m」，改一层即越线 |
| 气候分区 | 夏热冬冷 | 浙江 |
| 抗震设防烈度 | 6 度(0.05g) | 钱塘区，见浙江省超限导则附录A |
| 所在省份 / 适用标准册 | ZJ / `["GB", "ZJ"]` | 显式打开浙江省册，MiC 方案才按省导则判定 |

限高 51 m 是本案例的**演示开关**：把 `height_max` 改成 52，则 17 层的 B / C / B′
（51.0 m）会被 C-01 剔除、只剩 A / D / E 参与比选；改成 49 则连 A（49.5 m）也出局。
一次改一个数字就能演示「硬约束把方案踢出排名」的全过程。

> **关于两册的实测结论**：本案例在 `--packs GB` 与默认 `["GB","ZJ"]` 下的硬约束
> 与排名**完全一致**（见 `_check-gb.txt` 与 `_check.txt`）。原因见第六节第 5 条——
> 不要在没有实测的情况下声称「开了地方册结论就变了」。

## 四、怎么用（三条命令）

```powershell
# 1) 只读检查：参数校验 + 硬约束 + 四维得分 + 帕累托 + 角色排名
uv run --project backend python scripts/check_demo_case.py --case data/schemes/demo-qiantang-fictional

# 2) 换个口径再看一遍：只按国标判（去掉浙江省册）
uv run --project backend python scripts/check_demo_case.py --case data/schemes/demo-qiantang-fictional --packs GB

# 3) 确认无误后导入本地 Demo 库（会先删掉同名项目再写入）
uv run --project backend python scripts/seed_mock.py --mock-dir data/schemes/demo-qiantang-fictional
```

导入后打开 <http://localhost:5173>，项目名是「杭州钱塘 · 保障性租赁住房 ·
装配式决策演示案例（虚构）」。`B改现浇_whatif.json` 会被挂到 B 之下（父方案由该文件
顶层的 `_whatif_parent` 指定），默认列表不显示，需要 `include_whatif=true` 或从 B 的
详情页进入。

第 1 条命令也可以直接用 Makefile 目标：

```bash
make case-check CASE=data/schemes/demo-qiantang-fictional
```

## 六、已知口径问题（录制前请先决定）

1. **`envelope_area` 的历史样例口径不对。** `data/schemes/mock/` 里 5 套方案的
   `envelope_area / volume` 约 0.106–0.114，物理上不可能（真实高层住宅体形系数
   一般在 0.25–0.45）。本案例按「外墙面积合计」重算，落在 0.13–0.31 之间。
   若要与旧 mock 对比，请注意两边的 G-04 分不可直接比。
2. **A 方案的楼层效率口径。** A 的 `gfa` 按计容面积给（4 栋 × 15 层 × 640 m²），
   而基底按 4 × 900 m²（总平面基底），两者不同源，导致 G-05 算出 1.41 > 1。
   演示若要点开 G-05，先把 `footprint` 改成 2560 并请专业组核对。
3. **规则本身的重复计权。** G-02 / K-01 用同一个字段 `std_floor_repeat`、
   G-03 / K-02 用同一个 `component_types`，因此施工维度的分数受同一件事影响两次。
   案例里的「施工友好」得分请按相对比较使用，不要当作绝对水平。
4. **D 与 C 的差别只在风险特征。** C 勾了「深基坑」、D 没勾，这是为了让结构维度
   有区分度，**不代表**两套方案的基坑条件真的不同；真实项目须由施工图判定。
5. **浙江省册在本案例里没有改变结论。** B 的 MiC 体系选的是「模块化全预制剪力墙
   结构」，ZJ-S-03 的表6.1.8 对该体系 6 度区限高 130 m，而 B 只有 51.0 m，
   所以 ZJ-S-01/02/03/04 全部通过、`--packs GB` 与开册结果一致。**要让地方册真正
   改变结论，用 What-if 做一次现场演示**：在 B 上建副本，把 `mic_system` 改成
   「模块化框架结构」（该体系 6 度区限高仅 30 m），B 就会命中 ZJ-S-03 被剔除——
   同一套建筑、只改结构体系类型，国标看不出问题、省导则直接拦下。这是本案例
   最值得录的一段，但必须现场生成，不能用预设数据假装已发生。
6. **规模一变大，Q-05 / Q-06 必然低分。** 本案例单栋 60–102 户、每层 4–6 户，
   落在计分区间内所以看不出问题；一旦换成真实公租房那种规模（1572 户、10 栋 25 层），
   Q-05 会掉到个位数、Q-06 只剩 2.4–30 分，**品质维度被这两条压住，A 与 B 的差别
   几乎消失，五个角色全部选同一个方案**。原因是这两条指标的计分区间按普通商品住宅
   标定，而且 Q-06 的公式算的是「每栋每层户数」、名字却写「标准层交通规模」——
   **不是方案差**。已作为开发侧待办记入 [未决事项](../../../docs/open-items.md) 2.3.1；
   实测数据见[真实案例 README 第五节](../qiantang-real/README.md)。

以上第 1、2 条是本案例相对旧 mock 的**有意调整**，已经写进各方案 JSON 的
`_design_notes`，专业组核对时请重点看这两处。

7. **规则集扩容后，本案例会显示 15 条「数据不足」。** 土木侧第二轮往规则里加了施工安全
   （K-03～K-10）与结构构件（S-15～S-29）两组规则，需要一批新字段（基坑开挖深度、
   模板支撑高度、脚手架形式与高度、支护形式、基础形式与工作年限、剪力墙厚度、
   框架梁柱截面、筏板配筋率、错层声明等）。本目录的方案 JSON 建于扩容之前，**没有这些
   字段**，因此每条方案会列出十余条「数据不足」。

   这是**预期行为、不是缺陷**：缺字段时引擎报「数据不足」而不是判通过。
   两种处理方式：

   - **推荐**：参照[真实案例](../qiantang-real/README.md)的做法——新增字段逐条填上并
     在 `_design_notes.new_fields_status` 里说明哪些是实测、哪些是演示取值。真实案例
     已按此补齐，现在只剩 1 条 `S-29` 的规则侧误报（见未决事项 2.3.1）。
   - **或者**：保持留空，把「数据不足」当成演示内容——**「新增规则要什么数据、系统就
     告诉你去补什么」**，这本身就是规则集可扩展的证据。

   注意：补这些字段**不会改变**本案例的六个方案原有得分（四维得分只看指标规则），
   只影响合规提示的数量。

## 七、维护约定

- 改任何方案数值后，重跑第四节第 1 条命令，并把 `_check.txt` / `_check.json`
  一起更新；`_check*.txt` 是**证据文件**，不要手改。
- `data/schemes/mock/` 保持不变（T6 的回归测试 `backend/tests/test_mock_data.py`
  与前端快照都依赖它）。本案例是**新增**目录，两条数据线互不影响。
- 要让本案例成为前端离线演示与快照的默认样例，需要另外改
  `scripts/export_frontend_fixtures.py`、`frontend/scripts/sync-mock.mjs` 与
  `backend/tests/agents/conftest.py` 里的文件清单，并重新导出
  `frontend/src/mocks/fixtures/data.json`；那是独立的一次改动。
